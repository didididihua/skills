# 技术方案

以需求设计（或 PRD）和原型为输入，读相关服务的代码，写出怎么实现：配置端、每个场景的处理流程、数据与接口、可用性、测试方案、待确认与风险。读者是产品、研发、测试三方，所以每章开头先写结论，代码证据放到折叠块和附录。

模板：`templates/tech-design.md`。关键取舍写进决策记录（`decisions.md`），正文用「决策 N」引用。

## 步骤

1. **收集输入。** 需求设计或 PRD、原型（还没有又涉及页面时，先问用户要不要先画原型）、三方接口文档。按 profile 加载相关服务的资料。
2. **读代码。** 每个场景找到触发点和现有链路，记下 `[仓库] 文件:行号`，确认代码基线（`origin/master` 的提交）。管理端请求的链路也要查（前端 → 网关 → 服务）。
3. **先定方案。** 优先复用现有流程和现有上限（比如在原有循环里加一个渠道），只有现有结构撑不住时才设计新的子系统，并写清楚撑不住的条件。每个关键取舍写一条决策记录。
4. **写文档。** 复制模板，按章节填写。配置端按原型页面写；每个场景用固定结构：概况、业务规则、处理流程、改动点、异常与边界，最后是测试要点（`::: fold`，默认折叠）和现状调用链（`<details>`）。
5. **画图。** 按 `diagrams.md` 选图；每张图下写 `::: explain`。
6. **构建检查，交给用户。** 见 `SKILL.md` 的步骤 7、8。

## 章节结构

| 章 | 内容 | 主要读者 |
|---|---|---|
| 0 概述 | 一页看懂（结论、指标行、关键设计、要拍板的事、主要风险）、背景与范围、与 PRD 的差异 | 全部 |
| 1 总体设计 | 改动全貌（`::: board` + 改动清单）、上下游影响（含三方平台）、总体架构（`::: arch`）、公共能力 | 研发 |
| 2 配置端设计 | 按原型页面写接口、字段、保存校验、存储、改动点、测试要点 | 研发、测试 |
| 3 场景设计 | 每个场景一节，固定结构 | 全部 |
| 4 数据与接口 | 数据模型与存储、接口（请求示例用横向切换）、并发幂等与异常、容量与内存 | 研发 |
| 5 可用性评估与保障 | 监控告警、灰度降级回滚、数据处理、安全权限、资金安全、未来演进 | 研发 |
| 6 测试方案 | 范围与环境、验收用例的变化、补充用例、回归范围 | 测试 |
| 7 待确认与风险 | 开工前必须确认（B）、详设阶段确认（D）、风险（R） | 产品、研发 |
| 8 实施计划 | 工作量、上线顺序（`::: steps`）与回滚 | 研发 |
| 附录 | 代码事实、编号与规范、三方确认清单、配置项、SQL、代码基线与路径 | 研发 |

关键设计决策不写在章节里，单独写在决策记录：一览表加每条决策的背景、选择、理由、代价、未采用、关联和状态。团队有自己的技术方案模板时，按 profile 里的章节对应关系重排。

## 和需求设计的关系

- 有需求设计时：0.2 背景与范围只写一段并引用需求设计；0.3 与 PRD 的差异不再建表，写「见需求设计 §6」，只补充技术方案新发现的冲突（用新的 G 编号）；第 7 章的 B 只放技术上新冒出来的问题，需求设计已有的直接引用编号。
- 没有需求设计时：0.3 和 7.1 按下面的规则完整写。
- 场景的业务规则引用需求设计的 BR 编号，只补充实现层面的规则（用场景缩写编号，如 `PM-3`）。

## 规则

- 目录在左侧；右上角切换四个部分；正文里的横向切换（`::: switch`）只用于同一内容的不同情况：现状与改造后、不同场景的请求示例、不同规模的估算、不同处理结果的时序。
- 设计在前、证据在后：正文写「怎么做、为什么」，代码调用链放 `<details>` 或附录。
- 概述里的「关键设计」卡片每张都要能单独看懂：先写要解决的问题，再写做法和代价，最后链接到决策 N。
- 「测试要点」默认折叠：写成 `::: fold 测试要点 【测试】`，摘要自动显示条数；第 6 章测试方案不折叠。
- 原型上的每个数字、字段都要写出取值来源（复用哪个接口、哪个字段）。现有数据给不出的列为开工前确认（B）：写清不做时页面怎样、要做的话怎么算、多少工作量，工作量合计注明按哪种结论算。
- 只写这个功能特有的设计。日志格式、脱敏、压测流量拦截这类团队通用规范不写。
- 缓存按需求评估：调用方慢、有调用配额或读多写少时才考虑；需要时写清楚缓存什么、多久、怎么失效，写在「4.4 容量与内存评估」；评估下来不需要就不写。
- 每条规则、每个待确认项都有编号和负责方标签；与 PRD 不一致的地方必须进差异表。
- **与 PRD 的差异**先写 PRD 要实现什么，再逐个列冲突点，按「什么场景 → PRD 要求 → 照 PRD 做会出什么问题（受什么限制、后果多大）→ 方案怎么处理、谁能感觉到差别」写，并标出改了哪些验收用例。每个冲突点各列一条待确认（要产品拍板的放 §7.1 的 B），写成能直接回答的问题，带选项和代价；用户感觉得到和感觉不到的冲突分开列。冲突点有两个以上时，在差异表下用「冲突点 / 场景 / PRD 要求 / 会出什么问题 / 方案怎么处理 / 待确认」对照表展开。
- 每个冲突点写清原因：是方案自己的取舍，还是三方平台的规定。三方规定造成的冲突要突出：写明是哪条规定、出自哪个接口版本，待确认的负责方加上三方，先问规定能不能放开，再列产品的选项。
- 冲突点只讲 PRD 和方案的差别；分页、去重这类实现细节写在场景章节。
- 写「只发 1 条」「不会重复」这类保证前，核对分批、分页的边界：只在一页或一批里成立的，要写明范围。
- 页面相关的设计引用原型编号（P1、P1-3），不在技术方案里重画页面。
- 改动点表的类型列用【新增】【修改】【复用】；图里新增节点用 `:::new`，时序图新增步骤用紫色 `rect`。
- 数字要有来源：代码默认值写出位置；生产值标「待查」；估算标【推断】。
- 不查生产数据库；需要数据时给出只读库 SQL，交给用户执行。

## 每个场景的固定结构

| 小节 | 写什么 | 读者 |
|---|---|---|
| 场景概况 | `::: facts`：触发、提交粒度、量级、涉及服务、对应的需求点和验收标准 | 全部 |
| 业务规则 | 编号表，引用需求设计的 BR，补充实现层面的规则 | 产品、测试 |
| 处理流程 | 时序图或流程图（`diagrams.md`），图下 `::: explain` | 研发 |
| 改动点 | `[仓库] 文件:行号`、改什么、【新增】【修改】 | 研发 |
| 异常与边界 | 情况、处理、用户或运营看到什么 | 全部 |
| 测试要点 | `::: fold`，默认折叠 | 测试 |
| 现状调用链 | `<details>` | 研发 |
