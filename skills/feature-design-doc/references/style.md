# 版式与写作规则

四个部分（需求设计、原型交互、技术方案、决策记录）共用这套规则。

## 固定规则

0. **一个功能一份 HTML。** 四个部分是同一系列：页面右上角四个按钮切换内容，左侧目录跟着切换，记住上次看的是哪一个；各部分的编号互相跳转。
1. **目录在左侧。** 章和节全部展开，滚动时高亮当前位置；窗口变窄时侧栏收窄，只有手机宽度（600px 以下）才变成顶部横条。
2. **横向切换只切状态。** 分段按钮用来切换同一块内容在不同情况下的样子：原型的页面状态、现状和方案、不同场景的请求、不同规模的估算。不用横向切换做章节导航。
3. **结论在前。** 每章第一段说清楚这一章的结论；一页看懂放在最前面，产品、研发、测试各自知道从哪读起。

## 颜色

| 含义 | 颜色 | 用在哪 |
|---|---|---|
| 新增 | 紫 `#6b4eff` | 标签、原型编号、改动标注、图里的新增节点和步骤 |
| 改动 | 琥珀 `#c77700` / `#e09a2b` | 同上 |
| 现状、不变 | 灰 `#8792a2` | 同上 |
| 强调、导航、链接 | 蓝 `#0e8bda` | 目录当前项、章节号、链接 |
| 已确认、通过 | 绿 `#14885b` | 状态标签、结论提示块 |
| 风险、阻塞 | 红 `#d14343` | 风险等级、阻塞项 |
| 角色 | 产品品红、研发蓝、测试青 | 角色标签 |

底色是冷灰画布 `#edf0f4`，表格、图、卡片、提示块是白纸；代码块用深色。颜色只表达含义，不做装饰：同一种颜色在全文只代表一件事。图里的配色和这里一致，见 `diagrams.md`。

## 版式

- 正文 15px，行距 1.75；段落宽度不超过 800px，表格、图、卡片用满内容宽度（最宽 1200px）。
- 字号阶梯：12、13、14、15、16.5、19、28、40；代码 12.5px。图里的文字不小于 12px。
- 圆角阶梯 6、10、14、18；嵌套的圆角向内递减。
- 阴影只用在浮起的原型舞台上；提示块不用彩色左边线。
- 动效只保留目录滚动、编号闪烁和切换，尊重系统的减少动效设置。

## 写作

- 简洁、专业，不写套话；一句话说一件事。标题、正文都不用「·」。
- 规则、改动点、异常、测试点、验收标准都用表格，第一列是编号，方便评审和测试引用。
- 编号约定：开工前必须确认 `B`，详设阶段确认 `D`，与 PRD 的差异 `G`，风险 `R`；需求点 `RQ-n`，业务规则 `BR-n`，验收标准 `AC-n`；场景规则用场景缩写加序号（如 `PM-1`）；配置端规则 `CF-n`；原型页 `P1`，原型编号 `P1-3`。编号一经发出不再复用，撤销的写明「已撤销」。
- 代码事实要能复查：写成 `[仓库] 文件名:行号`，附录给出完整路径和代码基线。结论标注【已确认】（代码或文档能直接证明）、【推断】（需要压测或联调验证）、【待确认】（需要别人给结论）。
- 设计内容保持可见；只有部分读者需要逐条看的内容默认折叠：测试要点用 `::: fold`（摘要显示条数），现状调用链、长代码、SQL 这类证据用 `<details>`。
- 页面上的每个数字、字段都要有数据来源。现有数据给不出的（要新统计、新存储或要三方提供），列进待确认，由产品决定是否一定要做；原型上用 `data-ask` 标出。
- 敏感信息不进文档：手机号用占位符，不写密码、Token；生产环境只查日志，不查数据库，SQL 交给用户在只读库执行。

## 构建与检查

```bash
cd <本技能目录>/scripts && PUPPETEER_SKIP_DOWNLOAD=1 npm install        # 首次；用本机 Chrome，可用 CHROME_PATH 指定
node build.mjs <任意一份 doc.md>                                         # 合成 【设计文档】<功能名>.html
node audit.mjs <doc.html> --widths 1440,1024 --shots /tmp/fdd-shots     # 每个视图都查：溢出、字号、锚点、脚本错误、图内文字重叠、截图
```

交付前确认：build 没有 warning；每个视图都没有页面级横向滚动、没有断开的锚点、没有脚本错误；1440px 下图不需要横向滚动，图里的文字没有重叠；原型的每个状态都切过一遍；从技术方案点几个原型编号和需求编号，确认能切过去并定位。
