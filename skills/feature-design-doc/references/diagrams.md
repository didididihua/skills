# 画图

图用来省读者的时间：一张图只回答一个问题，图下的图解说清怎么读。动笔前先说出「这张图要回答什么」，说不出来就不画，用表格或一段话。

## 选哪种图

| 要回答的问题 | 用什么 | 不要用 |
|---|---|---|
| 改了哪些服务、每个服务改什么（改动全貌） | `::: board` 分组看板 | 思维导图 |
| 系统分几层，谁在哪一层，哪些是新增 | `::: arch` 分层架构 | 把所有服务和连线塞进一张流程图 |
| 一次请求经过哪些服务、按什么顺序 | Mermaid 时序图 | 流程图 |
| 一段处理怎样分支、循环、在哪里结束 | Mermaid 流程图（`flowchart TB`） | 时序图 |
| 一条数据的状态怎么变 | Mermaid 状态图 | 流程图 |
| 表之间是什么关系 | Mermaid ER 图，只画表名和关系 | 把字段都画进 ER 图 |
| 先做什么后做什么（实施步骤、上线顺序） | `::: steps` | 流程图 |
| 待确认的事按负责方分组 | `::: board`，或按负责方分的表格 | 思维导图 |
| 同一块内容的现状和改造后 | `::: switch` 里放两张图 | 两张图上下排 |

## 每张图都要有

1. **图名写结论。** ```` ```mermaid title="每天一次批量发放：一个会员一年只发一次" ````；组件把图名写在名称后面：`::: arch 改了两个服务、加了一个任务`。不写「流程图」「架构图」这类空名字。
2. **图解紧跟在图下面。** 写 `::: explain`，2 到 6 条，按读图的顺序：从哪看起、关键步骤为什么这样做、和现状有什么不同、出错时走哪条线。用 `**3–5**` 指向时序图的步骤号，用 `**收集器**` 指向节点名。图解和图拼成一张卡片。
3. **颜色只表示改动类型。** 新增紫、改动琥珀、不变灰、外部系统虚线框；同一种颜色在全文只代表一件事，不用颜色做装饰。图例由构建自动生成。

## Mermaid 写法

构建时 Mermaid 统一渲染成 SVG：白底节点、深色连线、浅灰分组框；流程图用 ELK 排版，连线横平竖直，少交叉。

### 流程图

- 方向优先 `TB`。节点超过 20 个就按阶段拆成几张图，每张图回答一个问题。
- 节点文字最多两行，每行不超过 12 个字，第二行写补充：`A["计划发送<br/>每页 100 人"]`。
- 判断节点 `{}` 只写一个短问题（不超过 12 个字），比如 `{模板可用？}`；条件写在连线上：`B -- 可用 --> C`，细节写进图解。长问题会把菱形撑得很大。
- 改动类型写在节点后面：`:::new`、`:::mod`、`:::keep`、`:::ext`，另有 `:::warn`、`:::bad`。构建自动补样式和图例。
- 分组用 `subgraph 服务名`；一组就是一个服务或一个阶段，跨组的连线越少越好。
- 回到前面的连线（循环）最多一条。循环里步骤多时，把它收成一个节点（「逐页处理」），细节写进图解或另画一张图。
- 存储写 `[(库名)]`，消息队列写 `[/队列名/]`，外部系统加 `:::ext`。

### 时序图

- 参与者不超过 6 个。名称要短，每行不超过 14 个字；类名放第二行：`participant S as 计划发送<br/>SendServiceImpl`。名称里写「新增」「改动」「三方」，构建时参与者框自动上色。
- 加 `autonumber`，图解用步骤号说明。
- **不画自调用**（`A->>A: …`）：文字会压在步骤号和连线上。内部处理写成 `Note right of A: 计划置为发送中`。
- 消息文字不超过 26 个字，参数和细节写进图解。
- 新增的步骤用 `rect rgba(107, 78, 255, 0.08)` … `end` 包起来，构建时画成紫色虚线框，图例显示「新增」。
- `loop`、`alt`、`opt` 的条件写短：`loop 每页 100 人`、`alt 发券失败`。

### 状态图

- 状态写中文名和取值：`SENT: 已发送（SENT）`；转换写触发条件：`PENDING --> SENT: 平台接单`。
- 只画这次改动涉及的状态；终态用 `[*]`。

### ER 图

- 只画表名和关系，字段写进「数据模型」的表格。关系线上写业务含义：`plan ||--o{ plan_channel : "一个计划多个渠道"`。
- 新增的表在图解里点明；表多于 6 张时按业务拆开。

## HTML 组件

下面四个组件由构建直接生成 HTML，不经过 Mermaid，排版稳定。完整语法见 `components.md`。

**分组看板 `::: board`**：每列一个分组（服务、需求点、负责方），每行一个条目，开头的【新增】【修改】【复用】决定颜色；`|` 后面是补充说明。

```markdown
::: board 改动全貌：两个服务改动，一个新任务
- **会员服务 member**
  - 【复用】生日字段 | 会员资料已有，只读
- **营销服务 marketing**
  - 【新增】生日礼规则 | 配置页、保存校验
  - 【新增】每日发放任务 | 按生日批量发券
  - 【修改】发券接口 | 增加来源「生日礼」
:::
```

**分层架构 `::: arch`**：每个一级条目是一层，二级条目是这一层里的组件：`名称 【类型】 | 说明`。层之间自动画向下的箭头；`{ext}` 把这一层画成虚线框（外部系统）。

```markdown
::: arch 生日礼只改营销服务，通知走现有通道
- **运营后台** 配置入口
  - 生日礼设置页 【新增】 | P1
- **业务服务**
  - 营销服务 marketing 【修改】 | 规则、发放任务、发券来源
  - 会员服务 member 【复用】 | 按生日查会员
- **通知** {ext}
  - 订阅消息、短信 【三方】 | 现有通知通道
:::
```

**步骤 `::: steps`**：按顺序编号的竖向时间线；条目末尾加 `{par}` 表示其中几件事可以并行。

```markdown
::: steps 上线顺序
- **建表与配置项** 先上数据库变更，开关默认关
- **营销服务、会员服务** 两边同时发布 {par}
- **运营后台** 配置页上线
- **灰度** 先开一个品牌，观察一周再全量
:::
```

**图解 `::: explain`**：紧跟在图或组件后面，和它拼成一张卡片。条目写 `**键** 说明`，键是步骤号、节点名或区域；不写键就是普通条目。

```markdown
::: explain
- **1–2** 每天 9:00 由定时任务触发，先查出生日在发放窗口内的会员。
- **3** 发券前先查发放记录：今年发过的会员直接跳过，重试不会重复发。
- **4–6** 新增部分（紫框）：发券成功后才发提醒；提醒失败只记录，不影响券。
:::
```

## 构建会检查的事

build 对每张图给出 warning：自调用、参与者名称太长、消息文字太长、判断节点文字太长、节点超过 20 个、用了思维导图、ER 图里字段太多。audit 在浏览器里量每张图里文字的重叠和最小字号。有 warning 先改再交付。

## 反例

| 问题 | 例子 | 改法 |
|---|---|---|
| 连线交错 | 前端、网关、五个服务、两个库、三方平台画进一张流程图 | 用 `::: arch` 分层；调用顺序另画时序图 |
| 判断节点撑大 | `{开了提醒？预检模板：可发、版本一致、类型匹配}` | `{模板可用？}`，条件写在连线上和图解里 |
| 自调用压字 | `S->>S: 计划置 RUNNING` | `Note right of S: 计划置为发送中` |
| 颜色没有含义 | 思维导图每个分支一种颜色 | 用 `::: board`，颜色只标新增和改动 |
| 图上没有说明 | 15 步的时序图后面直接接下一节 | 加 `::: explain`，讲清关键几步和异常 |
| 参与者是长类名 | `participant S as SendSmsPromotionalScheduleServiceImpl` | `participant S as 计划发送<br/>SendServiceImpl` |
| 一张图讲三件事 | 一张流程图同时画配置、发送、回执 | 拆成三张，各配图解 |
