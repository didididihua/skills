# 需求设计

需求设计回答「做什么、为谁做、做到什么程度算完成」。主要读者是产品和测试，研发用它对齐范围。它写在原型和技术方案之前：PRD 写清楚的地方不照抄，重点写 PRD 没说清、和现状冲突、需要拍板的地方。

模板：`templates/requirement.md`。组件语法见 `components.md`，画图见 `diagrams.md`。

## 章节

| 章 | 内容 | 主要读者 |
|---|---|---|
| 0 概览 | 一页看懂：一句话需求、目标和衡量方式、本期做与不做、要拍板几项 | 全部 |
| 1 背景与目标 | 为什么做，现状的问题（带数据），目标和怎么衡量 | 产品 |
| 2 角色与场景 | 谁在什么情况下用：角色表、使用场景、使用路径 | 全部 |
| 3 需求拆解 | 需求点到功能点：`::: board` 看全貌，表格写 RQ 编号、优先级、落在哪个原型页和方案章节 | 全部 |
| 4 业务规则 | BR 编号表：规则、例子、边界 | 产品、测试 |
| 5 数据与口径 | 每个数字和字段的定义、来源、现有数据能不能给出 | 产品、研发 |
| 6 与 PRD 的差异 | G 编号表，冲突点逐个展开 | 产品 |
| 7 验收标准 | AC 编号表：前置条件、操作、预期，对应哪条规则 | 测试 |
| 8 待确认 | B 编号表：写成能直接回答的问题，带选项和代价 | 产品 |

只梳理需求时写全这九章；全流程时，第 6 章和第 8 章是原型和技术方案的依据，它们直接引用这里的 G 和 B，不再另建表。

## 写法

- **一页看懂。** 一句话需求写成「给谁、在什么时候、提供什么」；目标写可衡量的结果（「生日券核销率」比「提升会员体验」好验收）。本期不做的事写在这里，并写不做的影响。
- **角色与场景。** 角色表写每个角色关心什么、在哪里操作；场景写成「什么人，在什么情况下，做什么，得到什么」，每个场景编号（S1、S2），后面的需求点和验收标准引用它。
- **需求拆解分三层。** 需求点（PRD 要解决的问题）→ 功能点（系统要提供的能力）→ 落在哪里（原型页 P、方案章节 §）。先用 `::: board` 按需求点分列画全貌，再用表格逐条写 RQ 编号、优先级（必须、应该、可选）和去向；只有需求设计时，最后一列写「待原型」「待方案」。
- **业务规则每条带例子。** 「会员 3 月 5 日生日，提前 3 天发，则 3 月 2 日 9:00 发券」比抽象描述好懂。边界单列：闰年 2 月 29 日、跨年、规则修改后当天怎么办。
- **数据与口径。** 每个数字写清怎么算、从哪取、多久更新。现有数据给不出的标【待确认】，写清两种结论：不做时页面怎样，要做的话需要什么数据、多少工作量。
- **与 PRD 的差异。** 写法和技术方案相同：先写 PRD 要实现什么，再逐个列冲突点，按「什么场景 → PRD 要求 → 照 PRD 做会出什么问题 → 建议怎么处理、谁能感觉到差别」写。每个冲突点在第 8 章各列一条待确认。三方规定造成的冲突要点名是哪条规定、哪个版本。
- **验收标准测试能直接执行。** 每条写前置条件、操作、预期结果，并对应至少一条 BR 或 RQ；异常和边界也要有验收标准。
- **待确认写成能直接回答的问题。** 带选项、推荐和代价，写清「找谁」。会改变页面的问题注明影响哪个原型页。

## 画图

- 需求拆解用 `::: board`，每列一个需求点。
- 使用路径用原型文档的 `::: journey`；只有需求设计时，用 `::: steps` 写运营或用户的操作顺序。
- 需要讲清现状流程时，画一张 Mermaid 流程图，标出要改的节点（`:::mod`）和新增的节点（`:::new`），图下写图解。
- 不在需求设计里画技术架构和时序图，那是技术方案的事。
