第一章

背景与目标

现在运营每月手工圈出当月过生日的会员，再批量发券：容易漏发和重复发，也没有提醒，会员常常不知道自己有券。目标是让系统按规则自动发券并提醒，运营只看效果。

关键设计

01每天一次批量发放
生日是固定日期，不需要实时触发；每天在发送时间跑一次，分页处理，重跑安全（决策 1）。
02发券和提醒分开
发券成功就写记录；提醒异步投递，失败只记录、可重试，不回滚券（决策 2）。
03一年只发一次靠唯一键
发放记录以「会员 + 年份」唯一，任务重跑、重复触发都不会多发（决策 3）。

第一章

决策

决策 1每天一次批量发放，不在会员生日当天实时触发已确认2026-11-21
状态
方案评审定稿
背景
生日券要在会员生日前按时到账。可以每天定时批量发，也可以为每个会员单独排一个定时消息。会员量大时，单独排的消息数量和会员数一样多，难以修改和取消。
选择
每个品牌每天在发送时间跑一次批量任务，分页拉人、逐个发券。
理由
生日是固定日期，没有实时性要求；批量任务改规则立即生效，停用只需关开关。平时每天约 1,650 人，峰值约 5 千人，2 分钟内完成推断。
代价
规则修改后次日生效，当天不会补发。
未采用
为每个会员排延迟消息：数量大，规则修改后要逐条取消。
关联
3.1、BG-1
决策 2发券和提醒分开，提醒失败不回滚券已确认2026-11-21
状态
产品同意
背景
提醒依赖订阅消息和短信，可能因为会员没订阅、短信余额不足而失败。如果提醒失败就不发券，会员会因为通道问题拿不到生日礼。
选择
发券成功就写记录；提醒异步投递，失败只记状态，运营可以手动重试一次。
理由
券是权益，提醒是通知；权益不应依赖通知通道的可用性。
代价
少数会员拿到券但没收到提醒，需要自己在券包里发现。
未采用
发券和提醒放在同一个事务里：通道异常会让券也发不出去。
关联
3.2、AC-4、RQ-3
决策 3发放记录以「会员 + 年份」唯一已确认2026-11-21
状态
研发评审
背景
任务可能因为重启、超时而重跑；规则也可能停用后再启用。需要保证每个会员每年只发一次（BR-1）。
选择
发放记录表的唯一键是 member_id, gift_year；先写占位记录再发券，插入冲突就跳过。
理由
用数据库唯一键做幂等，不依赖任务状态，重跑任意次都安全。
代价
会员当年修改生日后，不会再发第二次。
未采用
用缓存记录「今年已发」：缓存过期或丢失会重复发券。
关联
BR-1、4.3、BG-2
决策 4发送时间由运营配置，不按 PRD 的 0 点待确认2026-11-24
状态
等产品确认 B2
背景
PRD 要求生日当天 0 点发券并提醒。夜间推送打扰会员，且短信平台规定 21:00 到次日 8:00 不发营销短信（接口文档 v2.1），0 点提交的短信会被拒绝。
选择
运营在 P1 配置发送时间，9:00 到 20:00 整点，默认 10:00；发券和提醒都在这个时间。
理由
白天收到提醒，会员当天就能用；短信不会被平台拒绝。
代价
和 PRD 不同：会员不是在生日当天 0 点收到，验收用例 AC-1 的预期要改。
未采用
0 点发券、白天再提醒：券和提醒分在两个时间，会员先看到券却不知道是生日礼。
关联
G1、B2、P1-5、AC-1
