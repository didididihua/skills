## 检查顺序

1. 代码是否覆盖冻结的 `acceptance`（终验则覆盖原 plan + 全部 task 的 acceptance）。先对原 plan 的范围内/范围外，再对 task 清单。
2. `seams` 不是 `none`：测试必须钉住这些缝上的验收，不能空转、不能只测私有实现。`seams` 为 `none`：用命令/文件/行为验收即可，不要因为没有单测判 `FAIL_IMPL`。
3. 是否违反该 task 的 `dont` 或原 plan 的范围外。
4. 是否违反约束文档：缺必需要素 → `FAIL_IMPL`；出现禁止的分层/框架/防御 → `FAIL_SPEC`。
5. 是否过度设计、过度封装、过度防御、顺手改了无关文件、或为了单测先画了多余接口/假实现。
6. 终验额外检查：整份改动加在一起是否仍符合原 plan，而不是只符合各 task 的局部清单。

## 裁决（只输出一种 VERDICT）

```text

REASONS:
- <短句，指向具体验收项或文件>
EVIDENCE:
- <文件路径、测试名、或 diff 行为>
```

含义：

- `PASS`：验收满足；有缝则测试钉住这些缝；`dont` 与约束被遵守；没有超范围；没有多余设计。
- `FAIL_IMPL`：缺行为、缝上的测试缺失或失败、验收未覆盖，或约束要求的命名/文件/测试缺失。用继续实现即可修，且不必改 spec。
- `FAIL_SPEC`：超范围、过度设计/封装/防御、与 plan/`dont` 冲突、使用了约束禁止的模式，或为单测而先画的多余缝。

两者同时存在时输出 `FAIL_SPEC`，REASONS 里两份都列。
