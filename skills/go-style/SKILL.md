# Go 代码风格

把代码写成能顺着读完的业务过程：依赖从哪里来、这一段处理什么、错误怎样返回、资源由谁关闭，都能在相邻代码中找到。参考 Nexus Agent 的组织方式，结合用户已确认的 Go 可读性偏好。

## 使用前

先核对当前工作区、Go 版本、目标包约定和相关调用方。仓库有 `.codegraph/` 时按仓库规则先用 CodeGraph；没有则不为风格任务建立索引。保留用户已有改动。

编写 Go 时配合环境中已有的 `modern-go-guidelines` 技能，按目标版本运行其 `list`，不要把本技能的示例 Go 版本当作升级理由。本技能补充结构和排版偏好，不替代版本适用的语言规范。

只读取当前工作需要的材料：

| 正在处理 | 读取 |
|---|---|
| main、cmd、装配、生命周期 | [入口与装配样例](references/entry-and-wiring.md) |
| CRUD、字段更新、DTO、业务枚举 | [可编译的业务样例](examples/model_service.go)，必要时看[行为测试](examples/model_service_test.go) |
| FFMAAS 的 API、业务或 data 层 | [FFMAAS 适配与 proto / ent 样例](references/ffmaas.md) |
| 需要核实哪些做法来自 Nexus | [源码依据与取舍](references/source-map.md) |

## 写法与取舍

### 入口和依赖要直接

- `main` 负责进程层动作；可失败的初始化放在返回 `error` 的 `run` 或已有应用入口中。资源获取成功后紧邻注册清理，辅助函数不调用 `log.Fatal` / `os.Exit`。
- 按真实依赖排序组织启动：配置与校验、基础设施、安全与运行组件、业务装配、HTTP 绑定、运行与退出。用空行隔开阶段，必要时加一句解释。阶段不是必须新增的函数或包。
- 用构造函数显式注入依赖。多个服务确实共享装配资源时，可用具名字段的 `Deps`；依赖少就保留直接参数。不要把全量依赖容器传给每个业务方法，也不要为每个结构体机械创建接口。
- 服务集合只服务于装配或既有的业务协作。构造、全局注册、启动后台任务要有可辨认的边界；需要执行查询的初始化明确返回错误。
- 谁启动 goroutine，谁说明取消和等待方式。退出按实际生产依赖收尾；一次关闭链共享期限，不能给每一步重新计算完整超时。使用框架生命周期时只保留一个信号与 shutdown 控制方。

### 一段代码完成一个逻辑阶段

业务函数通常沿“校验 / 授权 → 读取 → 业务判断 → 更新 / 持久化 → 返回”阅读；按项目现有安全和业务顺序调整，不为模板重排授权检查。

错误紧接产生它的操作处理；失败提前返回，让主路径保持平直。简单透传保留一行，有额外语义才拆出命名函数。不要把同一过程切成大量只有一行的包装函数。

模型调用、工作流、工具调用继续通过已有运行组件协作；不要因为示例里出现网关、熔断、缓存或 worker 就增加这些功能。

### 可读性优先于行数

- 标准库、第三方库、当前模块 import 分组；组内交给 `gofmt` 排序。
- 长签名、长调用、复杂字面量按参数或字段展开。DTO 映射逐字段写清；嵌套结构独立缩进。
- 长 builder 链（尤其 ent）逐方法换行，复杂 `Where` 条件逐项列出。
- 参数校验、查询、判断、保存、响应构造之间留空行；一个操作和它的错误处理留在同一段。
- 短构造函数、短返回和简单表达式可保留一行。不设机械行宽，不把多条赋值、关闭或返回塞进同一行。
- 注释优先解释职责、约束和原因，例如“缺省字段保留原值”“先等回调再刷队列”。避免把每条语句翻译成中文，也不复制教学章节号和装饰性分隔符。

### 业务语义用类型和字段表达

- 请求、持久化对象、运行时描述符、对外 DTO 各有职责；不把整个请求对象无条件覆盖数据库对象。
- PATCH 的“未提供”和“明确设为零值”分别处理；`false`、`0`、空字符串是否允许清空以既有契约为准。指针 / proto `optional` 不用普通 getter 或 `cmp.Or` 抹平存在性。
- 状态、协议、类型、策略等有限业务概念使用已有命名常量。按概念区分供应商状态、健康状态、模型状态，即使底层值相同也不混用。普通文案和 JSON 字段名不机械常量化。
- 保留已有乐观锁、事务、软删除、审计、分页稳定排序和授权条件。读后写样例不代表可以删掉持久化层的并发校验。

### 错误和日志保持可追踪

有语义边界时用 `%w` 补充操作上下文，用 `errors.Is` / `errors.As` 判断错误；已有业务错误体系继续复用，不另造一套。

底层原因与用户可见信息按现有规则分离。采用结构化日志，记录定位问题所需的业务标识，不记录完整请求、配置、密钥或密码。低层已返回的错误不在每一层重复记录。

## 改造范围与完成标准

风格任务默认保持现有接口、存储语义和包结构。只做当前调用链需要的调整；发现行为缺陷时说明触发条件，再把修复和排版改动区分清楚。FFMAAS 的额外硬约束见适配文档。

完成前查看实际 diff：依赖来源是否清楚，逻辑阶段是否易读，字段存在性和错误匹配是否保留，是否误改生成物。运行 `gofmt` 和与改动相关的编译 / 测试；涉及行为变化时验证对应边界，不为纯换行编写镜像测试。报告实际通过与跳过的范围。

随附业务样例只用标准库，在 `examples` 目录可执行 `go test ./...`；它是写法参考，不是要求目标项目复制的分层或数据访问实现。
